## 1. 長く眠っているプールを解放する(4-E の3段目)

### いつやるか
- VRAM が足りなくなってきたとき
- Profiler の「Particles」で、Pools の数と Total Capacity が大きいまま減らない場面があるとき
  (たくさんのアセットを一度だけ使って、そのまま使わなくなる作りのとき)

### 今の状態
- 眠っているプール(最後に出してから最大寿命 + 0.5 秒経ったもの)は、更新も描画も飛ばしている(4-A)。
  **GPU の時間は使っていないが、バッファ(VRAM)は持ったまま**。
- 1プールの大きさ : 粒 64 バイト + 空き番号 4 バイト + 生存リスト 4 バイト = 1粒あたり 72 バイト。
  容量 10000 なら約 720KB。
- アセットが捨てられたプール(シーンの切れ目)と、容量が変わったプールは、もう解放・作り直ししている(4-E の1・2段目)。

### やること
1. `ParticleBufferManager` に「最後に使った時刻」`m_lastUsedTime` を持たせる。
   プールを作ったとき(`CreateParticleDataAsync`)と、命令を送ったとき(`UploadEmitData`)に入れる。
   ※ `m_lastEmitTime` は「一度も出していなければ眠っている」の判定に使っているので、作ったときには入れない。混ぜずに別に持つ。
2. `ParticleData.h` に `PARTICLE_POOL_RELEASE_IDLE_SECONDS`(30〜60 秒。0 なら解放しない)を足す。
3. `ReleaseUnusedPools` に条件を足す : 「眠っている(`!IsAwake`)」かつ「最後に使ってから上の秒数が経った」かつ「ロード中でない」→ `DestroyPool(handle, "長く使われていない")`。
4. `DestroyPool` と `Release` で `m_lastUsedTime` も消す。

### 気をつけること
- 解放したプールを次に使うときは作り直しになり、最初の粒が数フレーム遅れる(準備中の命令は持ち越すので、消えはしない)。
- 死亡エフェクトのように「たまにしか出ないが、出るときはすぐ出てほしいもの」は、Fixup で Warmup していても時間が経つと解放される。
  秒数は長めにする。気になるアセットだけ残したくなったら、アセット側に「解放しない」フラグを足す。

### 確かめ方
しばらく出していないアセットのプールが、ログ「プールを解放しました(長く使われていない)」とともに消えること。
もう一度出すと作り直されて、数フレーム以内に出ること。

## 2. 更新も生きている粒の数ぶんだけにする(4-F)

### いつやるか
- PIX で `UpdateParticleShader` の Dispatch が目立って重いとき
- 特に「起きているが粒がまばらな、容量の大きいプール」がある場面(容量 10000 で、実際に生きている粒は数百、など)

### 今の状態
- 描画は生きている粒の数ぶんだけ(4-C : 生存リスト + ExecuteIndirect)。
- 更新は **容量ぶん** Dispatch している(1スレッドが粒1つ。死んでいる粒はすぐ抜けるが、スレッドは立つ)。
- 眠っているプールは更新ごと飛ばしている(4-A)ので、効くのは起きているプールだけ。

### やること(生存リストを2本で回す)
1. プールに生存リストをもう1本持たせ、「今のリスト」と「次のリスト」を毎フレーム入れ替える。数(カウンター)もそれぞれに持つ。
2. 発生(Emit)は、作った粒の番号を **今のリスト** に積む。
3. 「今のリストの数」から Dispatch の引数(スレッドグループ数)を作る、1スレッドの小さな CS を足す。
4. 更新(Update)を間接 Dispatch にする。今のリストの数ぶんだけ回し、生き残った粒を **次のリスト** に積む
   (次のリストの数が、そのまま描画のインスタンス数になる。4-C の drawArgs を兼ねられる)。
5. GraphicsEngine に `D3D12_INDIRECT_ARGUMENT_TYPE_DISPATCH` 用のコマンドシグネチャを足す(DrawIndexed 用の隣)。
6. 状態の約束は 4-C と同じ(フレームの頭は COMMON、使う前に明示で遷移、FinishFrame で COMMON へ戻す)。
   Dispatch 用の引数バッファも INDIRECT_ARGUMENT にしてから使う。

### 気をつけること
- 空き番号を返す処理(寿命が尽きた粒をデッドリストへ)は、更新が回る粒にしか届かなくなる。
  「生きているのにどちらのリストにも入っていない粒」が出ると、二度と更新も返却もされずに席が漏れる。
  リストの入れ替えと数のリセットの順番を、図に描いてから組むこと。
- 新しく作ったプールは、最初のフレームで「今のリスト」が空になるよう、数を 0 で始める。

### 確かめ方
PIX で Update の Dispatch のスレッド数が「生きている粒の数」程度になっていること。
容量いっぱいまで出しては消える、を繰り返しても、出せる粒の数が減っていかないこと(席が漏れていないこと)。

## 3. そのほか保留していること

| 何を | いつやるか | 一言 |
|---|---|---|
| 半透明の粒を奥行きで並べ替える | 煙などの半透明の粒の重なりがちらつくとき | 4-C で描く順が毎フレーム入れ替わるようになった(生存リストをアトミックで積むため)。生存リストを奥行きで並べ替える |
| 粒バッファ本体の状態遷移を明示する | デバッグレイヤーが粒バッファについて指摘してきたとき | Update は UAV で書き、VS は SRV で読んでいる(暗黙の昇格のまま)。生存リストと同じ約束に乗せる |
| 転送用バッファの解放をコピー完了に合わせる | プールを作った直後に GPU エラーが出たとき | `GPUParticlePool::Init` の転送用バッファはコピーキューで使うのに、解放は描画フレームの完了待ちに合わせている。`ExecuteAsyncCopy` の完了コールバックで手放す |
| 発生の Dispatch をプールをまたいでまとめる | PIX で Emit の Dispatch 数とバリアが目立つとき | 今はプールごとに 1 Dispatch + UAV バリア。書き込み先(UAV)がプールごとに違うので、まとめるにはバリアの張り方から変える |
| GPU 時間の計測 | 上の「いつやるか」を PIX なしで見たくなったとき | Profiler の `DrawCoreTimings` が空のまま。タイムスタンプクエリで GPU 時間を出す |
